n-dx vs Spec Kit
for the codebase you already have

Spec Kit, OpenSpec, and Kiro start from intent you write down: specify, plan, task, implement. n-dx starts from the repo. sourcevision maps the tree, rex keeps a living PRD, hench executes the next task.

The difference that matters

Spec-first is the right loop
when you already know what to build.

n-dx is the other start: what is already here, and what to fix or finish. You can still add work in plain language with ndx add "Add SSO support" .

1
Analyze the tree

ndx analyze . runs sourcevision and writes AI-readable context. Files, imports, architectural zones, React catalog.

2
Propose a living PRD

ndx recommend . turns findings into epics and tasks. You accept or reject them. The spec is derived from the code.

3
Execute the next task

ndx work . has hench pick the next task, brief it with codebase context, and run a tool-use loop.

4
Stay current

ndx self-heal re-analyzes, recommends, executes, and acknowledges completed findings so they do not regenerate.

The useful claim is that the spec can be regenerated from the tree. If the last six months were vibe-coded, use the vibe-cleanup guide.

n-dx

Repo-first CLI

CLI-first toolkit from En Dash. Install @n-dx/core, then analyze, recommend, work, and start. Built for Claude Code and Codex. PRD in .rex/. Rex and SourceVision expose MCP.

  • Starts from an existing codebase scan
  • Living PRD, re-derived when the tree changes
  • Hench executes the next accepted task
  • Elastic 2.0 (source-available, not OSI)
ndx analyze . && ndx recommend . && ndx work .
github.com/en-dash-consulting/n-dx →

GitHub Spec Kit

Spec-first toolkit

Portable MIT toolkit. Install specify-cli, write a constitution, then specify, plan, task, and implement through the agent you already use. Specs are markdown in the repo. GitHub documents existing-project adoption. 2026 writeups still treat it as structured and often greenfield-leaning.

  • Constitution, then specify / plan / task / implement
  • Works with Copilot, Claude Code, Gemini, Cursor, and others
  • Markdown artifacts in the repo
  • MIT license
specify-cli  ·  /speckit.implement
github.com/github/spec-kit →

OpenSpec

Delta-first CLI

Lightweight CLI from Fission-AI, built brownfield-first. Changes are deltas (ADDED, MODIFIED, REMOVED) against a source-of-truth spec. The loop is propose, apply, archive. You spec the slice you are changing. It does not scan a repo into a PRD. License is commonly cited as MIT.

  • Change deltas, not a full-tree analyzer
  • Propose, apply, archive
  • Agent-agnostic apply step
  • MIT commonly cited; confirm the LICENSE file

AWS Kiro

Agentic IDE

An agentic IDE, not a CLI you add to an existing editor. A prompt becomes requirements, design, and tasks, then its agents implement. Typical files: requirements.md, design.md, tasks.md. Commercial AWS product. Formal requirement checks and Agent Hooks are on the public pitch. The workflow lives in Kiro.

  • Prompt to a spec set, then implement
  • Built-in agents; editor and spec are one product
  • requirements.md / design.md / tasks.md
  • AWS commercial license

Who should pick which

Four jobs. Pick the tool that matches the job.

Having people on the repo with you is consulting, not a CLI flag. The picks below are about the product, not the services bench.

Pick Spec Kit

You will write the spec before the code.

You want the portable SDD workflow most teams already recognize, you switch agents, and MIT is what most open-source buyers expect.

  • →
    Agent-portable: Copilot, Claude, Gemini, Cursor, and others
  • →
    Constitution plus specify / plan / task / implement
  • →
    OSI-friendly MIT license
Pick OpenSpec

You are changing one slice at a time.

You want a thin delta layer on an existing system, not a codebase analyzer or a full PRD tree.

  • →
    ADDED / MODIFIED / REMOVED against a source-of-truth spec
  • →
    Propose, apply, archive. Agent-agnostic apply.
  • →
    Not a cleanup analyzer and not a living PRD
Pick Kiro

You want SDD inside an IDE.

You are fine on AWS, and you want agent, editor, and spec as one product.

  • →
    Prompt becomes requirements, design, and tasks
  • →
    Built-in agents. The workflow lives in Kiro.
  • →
    Commercial AWS product, not a CLI you drop into Cursor
Pick n-dx

The repo already exists.

The plan has drifted from the code, or a prototype became production without a spec. Analyze the tree, keep a PRD that can be re-derived, then execute.

  • →
    Existing-codebase scan, not a blank constitution
  • →
    Living PRD in .rex/, re-analyzed each cycle
  • →
    Hench executes. Built for Claude Code and Codex.
When not to pick n-dx

Three real gaps. We will not talk past them.

Do not pick n-dx if you need a large community, an OSI-approved license, or an agent-agnostic install. Those are real gaps.

⚖
You need an OSI-approved license The code is public. The license is Elastic 2.0, not MIT. ELv2 allows internal use, modification, and distribution, with a hosted-service restriction. Spec Kit is MIT. The precise term for n-dx is source-available.
👥
You need a large community n-dx listed 16 GitHub stars on 21 Aug 2026. Spec Kit, OpenSpec, and Kiro are the names in the 2026 lists. If ecosystem size is the buying criterion, pick one of those.
⇄
You need an agent-agnostic install n-dx is built for Claude Code and Codex. Spec Kit and OpenSpec are written to ride whatever agent you already use. If you switch models every week, start there.

FAQ

Four questions we keep getting.

Is n-dx a Spec Kit alternative?

Same category, different start. Spec Kit is spec-first and agent-portable. n-dx is codebase-first and built for Claude Code and Codex. Choose from the jobs above, not from invented checkmarks.

Why is n-dx missing from Spec Kit vs OpenSpec vs Kiro lists?

The 2026 roundups at Levelop, Augment Code, and thebcms name Spec Kit, OpenSpec, Kiro, and BMAD. n-dx is smaller and newer (16 GitHub stars on 21 Aug 2026). Absence from a list is not a quality score.

Can I use n-dx on a greenfield repo?

Yes. Quickstart covers an empty project. The product is aimed at existing systems. A blank folder that wants specify, plan, tasks will feel more at home in Spec Kit or Kiro.

Is n-dx open source the way Spec Kit is?

The code is public. The license is Elastic 2.0, not MIT. ELv2 allows internal use, modification, and distribution, with a hosted-service restriction. Spec Kit is MIT. OpenSpec is commonly cited as MIT; confirm the LICENSE file. "Open source" on the marketing site is informal. The precise term is source-available.
